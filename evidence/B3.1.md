# B3.1 private copy verification

B3.1 passed on the local filesystem profile. The work started at `209122bda598aa4480e9804ac7eb2003963bc09d`. The tested implementation is `0168e74896a4cc30b47a5c5aef72187f9f771bd0`.

## Observations

- Chromium enrolled and signed in using a virtual passkey. It uploaded 1,151 of 2,302 bytes, then got HTTP 409 when it attempted to finalize. After a Compose web service restart, the same browser session read the committed offset of 1,151 and sent the remaining bytes. Two concurrent finalization requests returned HTTP 200 and one asset ID. A photo-only journal submission then linked the asset. PostgreSQL and the private volume agreed on the original's byte count and SHA-256. The volume contained one original.
- The automated PostgreSQL test simulated an uncommitted file tail and a restart after the original's private filename existed but before the asset transaction committed. The first retry discarded the tail. The second adopted the original after verification. Before commit the journal returned 404 when asked to link the upload ID, and the static path returned 404. Staging cleanup removed the completed stage and preserved the original. A stale upload expired and its staged file was removed.
- A gap and a changed replay returned 409. An upload with the right length and a changed byte returned 422 at finalization. A file declared as the wrong recognized type returned 422. These failed finalizations created zero asset rows and zero original files. A same-household guardian, a guest, and a learner in another household got scoped 404s for another actor's upload operations. Finalization without CSRF returned 403.
- Migration 0005 upgraded an existing B2 database from four to five migrations. B2 fixture asset `7c2ced6c-08ae-4200-99f0-a63db6a62ba3` retained its ID, length and digest and received the default opaque media type.
- The independent reviewer checked the migration, account and household scope, row locks, both recovery boundaries, passive signature validation and staging expiry. The follow-up review found no B3.1 blocker.

## Decisions and outstanding checks

This slice uses the approved private filesystem mount, 8 MiB request parts, an 8 GiB per-original limit and 24-hour staging expiry after the last committed part. A deployment with multiple filesystem service instances must share the same private mount. Recognized formats receive a bounded signature check, and other project or source files can use the opaque type. A checksum or type mismatch requires a fresh submission key.

The GCS upload backend, browser picker and photo matching, authorized download and preview surfaces, and Drive link promotion remain pending. The sustained large-file boundary, independent instances sharing a mount, and hosted profiles were outside this rehearsal. T3 and the photo-match adapter are pending the remaining B3 slices.
