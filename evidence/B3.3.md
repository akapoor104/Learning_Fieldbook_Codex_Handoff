## Observations

- Chromium opened the signed-in guardian’s tournament moment. The guardian attached a JPEG, PDF, ZIP and MP4 in order, then used the keyboard on **Paste a Drive link** to save the fifth item, **Full recording**. Chromium blocked every non-Fieldbook request throughout the exercise. Four downloads matched their fixture hashes. The fifth displayed **Link only** and its local media URL returned 404.
- The guardian used **Keep a copy** to pick an 8,390,341-byte synthetic MP4. The test made the first upload request commit 4,195,170 bytes, then dropped the response. The link stayed link-only, its download returned 404 and the API rejected the incomplete upload ID. **Save copy** resumed at 4,195,170. After verification, the item displayed **Copy saved** in the same position under the same link asset ID and original URL. The download matched the source hash. The file spans two browser hash chunks.
- Concurrent repeats returned 204 and preserved the same backing original. Trying to replace it with a different verified original returned 409. The backing upload ID returned 404 at the media route while only the linked attachment was visible. PostgreSQL showed one promoted asset with the recording’s digest. The private volume hash agreed with PostgreSQL and the browser download.
- **Withdraw copy** returned the attachment to link-only. **Restore copy** reused the verified backing ID. Removing the source link made its download unavailable. Restoring it returned it to position four, ahead of a sixth item. PostgreSQL showed five active attachments and the sixth withdrawn at position five. Replaying a source submission kept its ID. Changing a source submission under the same key returned 409.
- The signed-in guest and a different household received the same 404 body for the private PDF, the separate photo and an absent UUID. None of the denials included a filename. The family MP4 returned 206 and the expected byte range, 416 for an unsatisfiable range, and length headers on HEAD. The download used an attachment disposition, octet-stream, private no-store caching and nosniff. Plain HTTP, JavaScript and credentialed HTTPS source URLs returned 422.
- The B3.2 photo suite on the B3.3 release exercised words-first and relinking. The photo-match adapter rehearsed photo-first across independent learner and guardian sessions. It observed one original and one link before unmatch, zero links afterward, and the original guardian and digest. Together with the five-item browser run, these cover T3.
- Migration 0007 upgraded the existing six-migration B3.2 database. Photo `861369ab-9f93-4a4f-a5d1-7ac9f53e191c` retained its length of 2,302 and original fixture digest. The new URL and copy-reference columns were null for that existing original.
- The independent reviewer checked family and inbox scope, source validation, passive downloads, current moment locks, immutable backing assets, replay and migration compatibility. The follow-up checked copy withdrawal, exact-copy restoration and position-preserving link restoration.

## Limits

**Keep a copy**, withdrawal and restoration belong to the actor who saved the link. The current view offers an undo for the latest withdrawal. That button disappears after navigation or reload. Original bytes and withdrawn attachment positions remain in storage. The upload picker accepts up to 8 GiB. The tested recording exceeded 8 MiB, and physical Android, multi-gigabyte files, GCS media, hosted deployment and real Drive credentials were outside this rehearsal. This slice verified private originals under guest and outsider sessions. The selected-photo guest grant and its separate preview are part of B5, so the exact granted-photo and unselected-PDF pairing remains untested.
