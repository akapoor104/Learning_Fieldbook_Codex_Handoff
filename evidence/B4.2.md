# B4.2 audited guardian diary access

Starting revision `7d3226c1f1ac6e3a31dfb4430823f2e632fc75b4`. Candidate `7d67c978d5088c3543671dba4b80ca9253c9a242`.

## Observations

- Two fictional guardians signed in separately and each used their own WebAuthn credential in Chromium to answer the diary-specific challenge. Finishing the challenge rotated the session and committed one event before returning the new cookie. The first guardian chose viewing and the second chose recovery. Both could read the selected learner’s seeded diary and original. The first used HEAD and a byte range. The second downloaded the complete file and verified SHA-256.
- A generic verification session remained ordinary. Wrong CSRF, a challenge used for the wrong purpose, use of another guardian’s challenge, a guest or learner trying to elevate, and attempts across households were denied. The active grant showed only the selected learner’s diary, excluding a sibling’s diary in the same household. The elevated session had no family list or family write access, and the diary entry endpoint accepted reads only.
- A temporary database trigger rejected audit insertion during verified completion. The endpoint returned 503 with no replacement cookie and PostgreSQL retained zero events. The original guardian session still opened the family journal and received 404 for diary records and files. The same assertion could not be replayed. A fresh assertion finished successfully, and two concurrent finishes with that assertion produced one 200, one 401 and one event.
- A logout using the pre-rotation token revoked the diary successor when supplied with that token’s valid CSRF token. The pre-rotation token received 401 for diary reads. After sign-out, replaying the rotated cookie returned 401 and the logged event remained. For the second guardian, a fixture-only trigger shortened the recorded grant to eight seconds. Keep-alive did not extend it. When the grant expired, the same account could see the family list again, while diary GET, HEAD and range requests returned 404.
- The learner’s history API returned the two distinct guardians, kinds, recorded UTC times and expiry times. Reloading preserved the history, a sibling’s history remained empty, and the elevated guardian’s history request returned 404. PostgreSQL rejected UPDATE, DELETE and TRUNCATE on the audit table, which kept the two original events.
- The independent reviewer checked session binding, the transaction, append-only storage and the same live database scope on record and media selectors. Follow-up changes recheck the grant when selecting the object and revoke a diary successor if sign-out arrives through the pre-rotation cookie.
