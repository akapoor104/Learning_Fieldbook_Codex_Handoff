# B4.1 diary record and file isolation

Starting revision `b449688bcd9ec50523a8c8fa1d9150a7a82d3444`. Candidate `902b94aaeb1f67340b04f11a4b44a97be1d14f2a`. The release server was built from the same app and migration source as this candidate. The last commit only changes the test fixture.

## Observations

- **My diary** opened the invented household fixture's diary entry `m6` after the learner signed in with a virtual passkey. The same session could reload `/diary/`, read the entry by ID, and download its original with the expected filename. A HEAD request showed the learner the filename, and a byte-range request returned the first 16 expected bytes. The family journal displayed the ordinary family entry and excluded the marker even for the diary owner.
- Both ordinary guardians, the named guest, a second learner in the same household, and the learner and guardian of another household received 404 for the diary record and file. A guardian completed the existing identity verification step and still received 404. Denied downloads had no attachment disposition. The owner’s family record, revision, attachment, comment, download and upload-status routes also excluded the diary record or file. The family photo inbox returned no diary attachment.
- An attempt to attach a diary original while creating a family moment, edit the diary via the family moment route, or give a family archive link that diary original returned 404. The original retained its identity and SHA-256. Independently of application checks, PostgreSQL refused direct cross-scope inserts into family moment attachments and the family photo inbox, and refused a family link’s attempt to reference a diary copy.
- The database's family selectors returned one ordinary moment and zero marker matches in note text or family filenames. Existing family photo candidates and downloads remained scoped. The selector checks cover the input for later family search, counts, thumbnails and export features.
- Migration 0008 applied to both a fresh database and a B3.3 database with committed family rows. Pre-existing moment `00000000-0000-4000-8000-000000000043` retained its note and visibility. Link `00000000-0000-4000-8000-000000000045` remained at position 0 and referenced original `00000000-0000-4000-8000-000000000044` with its previous checksum.
- An independent reviewer checked the migration, Rust selectors, file resolution and browser entry point. The reviewer also checked formatting, whitespace and Svelte diagnostics. Future family audit selectors should join the family moment view when reading legacy match events.

## Limits

This slice demonstrates read-only access to a synthetic diary. Production diary capture, editing, and encryption for text, filenames and originals remain open. Normal family uploads still use the family scope. The product has no full-text search, generated thumbnails, coaching, or export UI in this slice. Their family selector inputs were exercised in PostgreSQL. Separate audited guardian access, learner-visible history and expiry belong to the next diary slices. T4 and its `diary-scope` adapter remain pending.
