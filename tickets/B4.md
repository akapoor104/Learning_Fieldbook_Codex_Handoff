# B4 · Private diary

Design v0.8 · Acceptance T4 · Primary lane access

Each guardian has a separate time-limited path and the learner sees the event.

## Outcome

Separate diary, per-object/file authorization, two independent parental recovery paths, access history.

## Read only what you need

Use the numbered paragraphs in `reference/Learning_Fieldbook_Design_Spec_v0.8.md`, lines 118-126,411-414,694-706. Shared API decisions are in `contracts/README.md`. Scenarios S14.

## Assign one slice

### B4.1 · Isolate diary records and files

**Suggested change area** SQL. **Prerequisites** B1.3, B2.1, B3.1.

Implement family/diary visibility and a policy used by direct reads, search, counts, previews and export selectors.

**Inputs and suggested files** fixtures/household.json. migrations/, crates/fieldbook/src/storage/ and SQL-backed integration tests.

**Run** Run cargo test --workspace --locked with an isolated PostgreSQL 16 database. Inspect committed rows and original file hashes where relevant.

**Passing example** The learner may open the seeded diary. Ordinary guardian, guest and second household views exclude it.

**Counterexample** A diary marker is absent from thumbnails, suggested matches, all family lists and filenames.

**Suggested model** GPT-6.2 Sol for the integration or review.

### B4.2 · Record exceptional access before opening

**Suggested change area** Rust. **Prerequisites** B4.1.

Add independent guardian reauthentication, time-limited read-only access and an immutable access event visible to the learner.

**Inputs and suggested files** fixtures/household.json. crates/fieldbook/src/ and crates/fieldbook/tests/, plus web/src/ for a joint UI slice.

**Run** Run cargo fmt --all -- --check and cargo test --workspace --locked. For a UI join also run the relevant web tests.

**Passing example** Each guardian can open the diary separately. Two events identify the two distinct actors.

**Counterexample** Failed logging, expired elevation or a normal session cannot expose the diary. Sharing and coaching stay unavailable in elevation.

**Suggested model** GPT-6.2 Sol for the integration or review.

### B4.3 · Explain diary access to the learner

**Suggested change area** UI/QA. **Prerequisites** B4.2.

Add the on-screen privacy promise, access history and sign-out or expiry flow. Check original file routes use the same gate.

**Inputs and suggested files** fixtures/household.json. The relevant integration or device tests and their evidence.

**Run** Drive the named application flow against a disposable fixture. Run the owning Rust or web suite plus the specified device or operator procedure.

**Passing example** After two separately elevated views the learner sees both times and actors and can still journal.

**Counterexample** An expired or signed-out guardian returns to ordinary visibility, including on browser Back.

**Suggested model** GPT-6.2 Sol for the integration or review.
